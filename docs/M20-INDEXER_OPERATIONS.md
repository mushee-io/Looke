# M20 — Indexing and backend operations

**Source stage: bounded, disabled-by-default Ultra EVM testnet job orchestration, durable sanitized indexer heartbeat, and private operator diagnostics.** This does **not** deploy audited contracts, start a scheduler, repair a stale cursor, create Vercel staging, execute user trading, or prove any live testnet transaction.

## What M20 adds

- **`db/015_indexer_operations.sql`:** separate Looke-only `looke_indexer_operations` operator heartbeat table with stream key, last attempt, last success, last operation status, sanitized error class, consecutive failures, last indexed log count and last confirmed block. No credentials, customer identifiers, wallet records, accrued rewards, secret keys or funds. Applied to isolated Looke Neon staging. It does not replace the M13 atomic event-and-cursor transaction.
- **Hardened protected worker** `POST /api/indexer`: requires an explicit 32+ character `LOOKE_INDEXER_SECRET` with constant-time digest comparison. Records every authorized valid-stream result in the heartbeat, including caught-up or waiting states. A failure records only a coarse error class; unauthorized, malformed or unallowlisted streams cannot create heartbeat records. If canonical ingestion commits but heartbeat persistence fails, the response explicitly warns the **canonical cursor may have advanced** and requires inspection before retrying. No auto-rollback.
- **Separate monitor endpoint** `GET /api/operator/indexer/status` protected by a DIFFERENT 32+ character `LOOKE_INDEXER_MONITOR_SECRET`. Reports Ultra EVM testnet chain ID, RPC head and 12-block frontier, configured factory/allowlisted pool sources, canonical cursor hash status, last operator attempt/success, indexed count, bounded confirmed lag and readiness. A 503 marks unconfigured/unhealthy/stale/failed streams instead of suggesting they are operational. Canonical unknown due RPC outage is distinct from a demonstrated chain mismatch. The status is private; public readers continue to use the safe `/api/markets`.
- **Opt-in scheduler** `.github/workflows/indexer-staging.yml`: 15-minute schedule plus manual dispatch, but its only job is **skipped** unless the repository owner sets `LOOKE_INDEXER_SCHEDULER_ENABLED=true` in GitHub Actions Variables. `scripts/run-indexer.mjs` requires an HTTPS deployment origin, a 32+ character indexing bearer secret, optional separately scoped monitoring bearer, and at most eight manually reviewed pool addresses. It refuses loopback/internal hosts, redirects, invalid/duplicate pools, or responses without the correct Ultra testnet and telemetry marker. Every invocation handles **one factory + at most eight operator-listed pool sources** sequentially, for up to four bounded M13 250-block batches each. Exceeds neither 12-minute workflow timeout nor 25-second/request timeout in normal operation. Errors produce a failed GitHub Actions job, not guessed success.
- **Operational safety tests** `tests/indexer-operations.test.mjs` and `tests/indexer-scheduler-source.test.mjs`: strict URLs/pool lists, canonicality, lag/failure freshness decisions, safety gating and prohibited wallet signing. The existing M13 block-hash and transaction guards remain in place.
- **No secrets are configured by source control:** database migrations and GitHub workflow files can be merged without activating ingestion. Scheduled GitHub jobs cannot process any Ultra data until an authorized deployment and explicit opt-in are in place.

## Protected staging setup — manual operator gates

1. Confirm you have Vercel team ownership/permission to create and manage a Looke project. Earlier project creation returned HTTP **403**, and at the time of M20 no authorized protected Looke staging or verified deployment URL was available. Repository code/CI does not grant that missing permission.
2. Provision `looke-staging` under an authorized account/team with HTTPS, **preview protection**, separate secrets, strict `NODE_ENV` settings, region close to Neon, and an explicit Ultra **testnet only** chain. Connect GitHub repository `mushee-io/Looke` only when team access is confirmed. Never expose admin routes without bearer authentication.
3. Set Looke-only `DATABASE_URL` and apply schema migrations through `db/015_indexer_operations.sql` in dependency order (including `002` and `010`). Confirm DB TLS and a valid operational heartbeat table. **The database migration alone is not evidence of genuine onchain activity.**
4. Independently verify a real Ultra EVM factory (code, deployment block and security review). Supply server-side `LOOKE_FACTORY_TESTNET_ADDRESS`, `LOOKE_FACTORY_TESTNET_DEPLOY_BLOCK`, and optional independently audited/allowlisted pool sources under `LOOKE_ALLOWED_TESTNET_POOLS` plus `LOOKE_MARKET_POOL_START_BLOCK`. Never set a random factory address for the purpose of making the monitor green.
5. Generate two distinct **at least 32-character** random secrets: `LOOKE_INDEXER_SECRET` and `LOOKE_INDEXER_MONITOR_SECRET`, and set them **server side in Vercel**. Rotate any older 24-character operator tokens when upgrading the indexer endpoint. Public `NEXT_PUBLIC_` values must never contain them.
6. In GitHub repository settings → Secrets and variables → Actions, set Secrets `LOOKE_SCHEDULER_BASE_URL` (approved HTTPS deployment origin), `LOOKE_INDEXER_SECRET`, and optionally `LOOKE_INDEXER_MONITOR_SECRET` (matching the protected deployed values). Under Actions Variables, set `LOOKE_APPROVED_INDEXER_POOLS` to a comma-separated list only after pool review. Leave it blank for a factory-only trial. **DO NOT** set `LOOKE_INDEXER_SCHEDULER_ENABLED=true` until manual isolated staging verification has passed.
7. First test an operator `POST /api/indexer?stream=coins` with the authenticated bearer and then the private `GET /api/operator/indexer/status` with the **separate monitor bearer**. Inspect the canonical cursor/hash and heartbeat vs independent testnet explorer/RPC evidence. A non-empty log database is not an independent security audit.
8. After real testnet approvals and verification, deliberately set GitHub Actions Variable `LOOKE_INDEXER_SCHEDULER_ENABLED=true`, manually dispatch the workflow once, and review the bounded multi-batch outcome. Each scheduled run attempts at most 4 × 250 confirmed blocks per enabled stream; historical catch-up may require additional manual runs. Cron timing is best effort and GitHub Actions may delay jobs. No private keys are used.
9. Configure GitHub Actions job failure notifications and protected operator health polling. If the monitor reports a reorg/legacy cursor, **stop automatic runs** and perform an independently reviewed, documented replay; do **not** edit cursors or token/event rows through this workflow. Investigate missing/stale data, RPC outages and excessive lag. Scheduled monitoring is not a replacement for incident response.
10. Gate public launch on real Ultra EVM signed tx receipts, independent audit of contracts and data provenance, full frontend deployment/device QA, backup/restore, WAF/quota tests and operator ownership/permissions. No mainnet trading, NFT issuance, creator payouts or rewards are activated here.

## Known limitations

- The worker still trusts a configured Ultra RPC and 12-block delay. It does not prove independently verified event origins, validate every individual historical log against a second RPC, guarantee deep reorg immunity, or autonomously reconcile a divergent cursor.
- The heartbeat is a separate best-effort write after canonical ingestion. A server crash can leave it stale even if an event batch committed: **operator status must check the canonical cursor**, not treat heartbeat as financial finality.
- A running monitor reports operational progress only; no verified liquidity, token prices, rewards, assets or orders can be inferred. A newly configured source with no checkpoint is reported as NOT READY.
- This PR does not run GitHub Actions with secrets, create real Vercel staging, execute live Ultra indexer calls, or prove there are verified factory/pool addresses.

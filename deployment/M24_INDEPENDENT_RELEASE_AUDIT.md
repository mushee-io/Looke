## Full-row PostgreSQL backup / restore verification
1. Back up a genuine operator-owned PostgreSQL database with verified encrypted at-rest storage, operator-accessible recovery logs and a consistent point-in-time or quiesced source marker. A prior `LIMIT 50` sample is insufficient for complete recovery.
2. **Restore** the backup to a separately controlled nonproduction PostgreSQL host/database. Do not point `LOOKE_M24_RESTORE_DATABASE_URL` to the original. Configure distinct `postgresql://...?...sslmode=verify-full` or `verify-ca` connections and verify trust roots and actual TLS handshake independently.
3. Run `DATABASE_URL=... LOOKE_M24_RESTORE_DATABASE_URL=... npm run m24:full-restore-audit` on an authorized operator computer. This executable **never restores, creates or writes** databases. It checks actual TLS via `pg_stat_ssl`, starts repeatable-read **read-only** transactions, and walks **all rows** (bounded 100,000 records per table; 100 rows per batch) across 16 fixed social, moderation, Points, index and acceptance tables.
4. The digest algorithm uses PostgreSQL deterministic `to_jsonb(row)::text` serialization, length-prefixed row SHA-256 streaming, schema fingerprint and full row count. Comparison fails on missing table, schema drift, row-level difference, excessive row count, missing TLS or incomplete scan. `artifacts/m24/full-restore.json` contains digests and table counts, not private rows or database credentials.
5. Caveats: independently captured snapshots need an equal logical cutoff; live writes can create drift. This is *data and schema equality*, **not proof of backup authenticity, archive completeness, independent staff restore, RTO/RPO, lost encryption keys or service-level recovery**. A separate operator and independent auditor must inspect backup provenance, TLS, restore procedure, cross-service resources and real recovery logs, then sign off externally.

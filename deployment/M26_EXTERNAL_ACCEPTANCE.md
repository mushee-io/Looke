## M26 implementation, sources and limitations
- Moderator-only `GET /api/social/ops/m26` composes actual M25 signed-review register, M23 one-use wallet key-control proofs, real media/moderation and Points source reconciliations, M24 incident/rollback observations and external signed-document references. `?live=true` delegates to the existing authenticated real-provider and Ultra EVM/native RPC probe. Supplying `?assetKind=token&factory=...&tx=...` or `?assetKind=uniq&nativeOwner=...&factoryId=...&tokenId=...` checks actual current Testnet evidence, not a stored token claim or manufactured transaction.
- `011_dual_role_release_witness.sql` creates an **empty** append-only dual-role signature-reference ledger. `independent_security` and `independent_operator` require different allowlisted public wallets, each distinct from the current operator, original M23 evidence signer and M25 reviewer. Database uniqueness and `FOR UPDATE` on the existing M25 review serialize concurrent submissions to prevent same-role and same-wallet duplicate approvals. Signatures are scoped by exact Preview HTTPS origin and immutable commit, existing M25 review UUID, original M23 SHA-256 evidence, role, limited `hold` or `reference_acknowledged_unverified` decision and five-minute freshness.
- Recording requires existing moderator wallet session, CSRF-protected JSON, separate `LOOKE_M26_WITNESS_WRITES_ENABLED=true` (off by default), actual prior M25/M23 same-commit records and configured `LOOKE_M26_SECURITY_WITNESSES`/`LOOKE_M26_OPERATOR_WITNESSES`. Neither a wallet signature nor an allowlist verifies human independence or that document contents were reviewed. The new schema CHECK constraints permanently prohibit flags claiming this or enabling public beta. No GO or activation operation exists.
- Two one-use signed wallet keys are not two independently witnessed humans. To accept that gate operationally, observe two real separately controlled wallets and a genuine social login in a separately authorized Testnet session, independently record wallet ownership and anti-sybil evidence. This M26 module does NOT activate public login, social posting, or financial messages.
- Authentic Cloudinary provider media inspection must check real asset metadata, bytes, ownership and review/moderation logs. CI fixtures and SQL `media_status` alone are not provider proof.
- Ultra EVM creator coin requires an actual canonical CoinCreated tx on chain 18881 and current contract code. Native Ultra Uniq requires native factory + token ID + current owner at irreversible block. If records are missing, remain blocked; never infer a token from post metadata.
- Points reconciliation checks current eligible source against actual approved Points entries with bounded read-only scans. Manual counterparty/anti-sybil review and any point corrections need a separate human authorization.

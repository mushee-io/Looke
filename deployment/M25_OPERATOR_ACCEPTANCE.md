## What this milestone actually implements
1. **Signed external evidence review register.** Migration `010_operator_release_evidence.sql` adds an **empty** append-only table for all 11 M24 release gates. It is explicitly constrained against `beta_release_authorized`, `production_changed`, `external_security_approval`, `artifact_bytes_verified` and `real_human_identity_verified` being true. No demo activity, approvals, wallet keys, token, review or grant evidence is seeded. There is **no migration on Vercel build**.
2. **Real reviewer separation.** `GET /api/social/ops/m25` is read-only, requires an existing signed-in non-suspended moderator and actual PostgreSQL. It reads genuine M23 server-issued consumed nonces with actual cryptographic signatures, links to existing separately signed M23 artifact references bound to exact Preview SHA, reports actual media/moderation statuses, Points ledger and manual sybil review counts, M24 incident/rollback evidence and any live read-only Ultra chain/provider status requested. Reports *two keys* and **not** two independently witnessed human testers.
3. **Optional controlled review-reference writes, default OFF.** `POST /api/social/ops/m25` requires correct same-origin JSON, the existing moderator session, rate limit, `LOOKE_M25_REVIEW_WRITES_ENABLED=true`, and exact canonical `LOOKE_M23_PREVIEW_ORIGIN` + immutable `VERCEL_GIT_COMMIT_SHA`. No bypass to wallet authentication or real social posting is enabled. A reviewer distinct from both the operator and the earlier M23 evidence signer must be allowlisted by `LOOKE_M25_EXTERNAL_REVIEWERS` (general evidence) or `LOOKE_M25_RELEASE_REVIEWERS` (operator review). The external wallet personally signs **only** a nonfinancial public EIP-191 text containing the exact Preview origin/SHA, gate, existing signed evidence ID, SHA-256, decision and fresh five-minute timestamp. The server rechecks signature/reviewer/role/freshness/deduplication and stores an **acknowledgment of an evidence reference**, not an audit approval. `reviewed_reference_only` and `needs_more_evidence` are the only decisions.
4. **Two-wallet cryptographic isolation.** Before a witness-gate *reference* can even be logged, the backend queries at least two distinct, genuinely consumed one-use EIP-191 wallet challenges on the exact Preview SHA with unsuspended profiles. Having two keys is **NOT** proof of two independent people or an externally witnessed session. A different human must observe and independently sign actual field acceptance outside this API.
5. **Current provider, moderation, chain and Points checks.** `?live=true` delegates to the existing M21 provider inspection and read-only Ultra Testnet heads; if no real asset/provider records or credentials are configured it fails closed. `?assetKind=token&factory=...&tx=...` rechecks a canonical actual Ultra EVM Testnet 18881 receipt and current deployed token state, while `?assetKind=uniq&nativeOwner=...&factoryId=...&tokenId=...` rechecks native factory/token/current owner. An attached social post text alone is not chain proof. Points reconciliation remains source-backed and account-scoped; anti-sybil clustering and human identity are independent manual checks. No real transactions are signed or broadcast.
6. **Full database restore.** `npm run m24:full-restore-audit` compares all rows of **17 fixed M24 source tables** and their schema hashes on separately controlled TLS PostgreSQL endpoints, after an actual independent operator restores a consistent backup. It does not perform that restoration or establish backup provenance. The new M25 review table is **outside the existing 17-table baseline**; an independent reviewer must separately archive/verify this append-only evidence register before claiming full post-M25 database coverage. The database user requires least-privilege controls, actual TLS, backup logs, operator eyewitness evidence, and consistent source cutoff to validate a real disaster-recovery operation. A technical match alone never approves the release.
7. **Independent document bytes and scope.** `npm run m24:verify-evidence -- --file REPORT --evidence-id UUID --commit SHA` hashes an actual non-symlink regular file and checks its bytes against signed M23 SHA-256. This verifies only digest equality, not the auditor's identity/independence, methodology, security findings or remediation. Have a real security auditor inspect findings, test current deployments, and sign the final operational decision separately.
8. **Incident and rollback.** The M24 no-execution incident journal and runbook remain available. Operators must independently check Vercel alias `dpl_29EdVrfrJNTC5Q7gkZMcpaxLhQiG`, document genuine incident, restore to a separate host and rehearse rollback. No API or UI controls in M25 can perform deployment, rollback or enable any release. No background build automation is created.
